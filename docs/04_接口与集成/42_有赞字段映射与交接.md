# 42 有赞字段映射与交接（Mock / 官方预建映射 → 内部模型 / Q11 待确认）

## 1. 使用边界

本表描述仓库当前 Mock fixture、P1-1R 官方字段预建映射和内部 DTO/存储/处理规则。Q11 未确认，`FEATURE_REAL_YOUZAN` 默认关闭；真实店铺类型、能力包、实际接口版本、限流和回调验收仍须用授权测试店铺确认。

- Mock 店铺 `MOCK-SHOP-001`、订单/客户/SKU ID 均为虚构数据，不含真实个人信息。
- 管理接口与 webhook 是 CRM 内部接口；官方 endpoint 仅在 `RealYouzanAdapter/YouzanRemoteClient` 中使用。
- Adapter DTO 只用于适配层，内部订单仍由订单领域服务创建和确认。

## 1.1 P1-1R 官方字段预建映射

| 官方字段 | 内部字段或处理 | 规则 |
|---|---|---|
| 消息 `msgId`、`kdtId` | `event_id`、`shop_id` | 验签去重；租户由已保存的 `clientId + kdtId` 配置确定 |
| `order_info.tid` | `external_order_no` | 列表返回后仍需查询订单详情 |
| `order_info.update_time` | `external_updated_at` | 按 `Asia/Shanghai` 解析后转 UTC Instant；旧版本不覆盖新事实 |
| `order_info.status` + `pay_info` | `event_type/status` | `TRADE_PAID` 及支付后的待确认/待发货/已发货/交易成功进入支付核验；待付款和关闭状态不提前发权益 |
| `pay_info.payment` | `amount_fen` | 元字符串通过 `BigDecimal` 转整数分，禁止 float/double |
| `order_info.pay_time` | `paid_at` | 支付核验必填 |
| `pay_info.transaction` | `external_trade_no` | 仅单一交易号自动处理；多阶段/多交易记录进入支付异常 |
| `buyer_info.yz_open_id` | `external_customer_id` | 仍需人工客户链接，不使用手机号或昵称自动认领 |
| `orders[].item_id + sku_id` | `external_sku_id` | 存为 `itemId:skuId`，映射 ACTIVE CRM SKU 后才可建单 |
| `orders[].num` | `items[].quantity` | 必须为正整数 |
| 官方完整响应 | `provider_payload_masked_json/provider_payload_cipher` | 原文脱敏与 AES-GCM 密文分列；内部标准事件另存于既有 payload 列 |

活动 ID、CRM 承接方和权益有效期不从 Mock 推断，也不把有赞营销活动 ID 直接当 CRM `campaignId`；无明确映射时使用内部规则或进入异常。

## 2. Mock fixture 字段 → 内部字段/用途

| Mock 字段（JSON） | 必填条件 | 内部字段或处理 | 规则/失败边界 |
|---|---|---|---|
| `event_id` | 必填 | `crm_youzan_event.event_id` | 与 `shopId` 组成原始事件唯一键；重复返回 `duplicate=true`，不重复建单 |
| `event_type` | 必填 | 原始事件类型与处理分支 | 仅 `ORDER_PAID` 进入支付确认；其他类型不得提前发权益 |
| `shop_id` | 必填 | 各映射表 `shop_id`、同步 cursor | 店铺级隔离与幂等前缀，不等于真实店铺授权 |
| `external_order_no` | 必填 | `crm_youzan_order_map.external_order_no`、内部订单 `external_order_no` | 与店铺唯一映射一个内部订单，不覆盖已支付事实 |
| `external_customer_id` | 必填 | `crm_youzan_customer_link.external_customer_id` | 外部标识，不是手机号/昵称；未人工链接时 `CUSTOMER_UNRESOLVED` |
| `external_trade_no` | `ORDER_PAID` 必填 | 支付 `externalTradeNo` | 必须非空；Mock 支付幂等键为 `shopId:externalTradeNo`，重复不重复发权益 |
| `status` | 可选原始值 | 原始事件信息 | 不单独作为支付可信依据；支付由事件类型、交易字段、金额和领域状态共同校验 |
| `amount_fen` | 必填、正整数 | 创建订单 `payableFen`、支付 `amountFen` | 整数分；必须等于内部应付金额，否则 `PAYMENT_MISMATCH` |
| `paid_at` | `ORDER_PAID` 必填 | 订单/支付时间 | 必须带可解析时间；不得用接收时间冒充实际支付时间 |
| `external_updated_at` | 必填 | `crm_youzan_order_map.last_external_updated_at` | 旧于或等于已处理版本时按重复/旧版本，不覆盖新版本 |
| `order_type_code` | 可空 | 内部 `orderTypeCode` | 缺省 `REGULAR`；允许 `REGULAR/FLASH/PROMOTION`，不是官方默认 |
| `campaign_id` | 可空 | 内部 `campaignId` | 必须与 `campaign_batch_id` 同时存在且为有效活动批次 |
| `campaign_batch_id` | 可空 | 内部 `campaignBatchId` | 与 `campaign_id` 成对校验，失败进入同步异常/重试而非伪造活动 |
| `receiver_type` | 可空 | 内部 `receiverType` | 缺省 `PLATFORM`；允许 `PLATFORM/INSTITUTION` |
| `valid_to` | 可空 | 权益快照 `validTo` | 缺省由内部规则生成，不代表供应商默认有效期 |
| `items[].external_sku_id` | 每个明细必填 | `crm_youzan_sku_map.external_sku_id` → `crmSkuId` | 仅 ACTIVE 映射可建单；未映射/无效数量进入 `MAPPING_FAILED`，不发权益 |
| `items[].quantity` | 每个明细必填 | 内部订单行 `purchaseQuantity` | 必须为正整数，并满足内部上限；不能用套餐总次数替代项目明细 |

原始 JSON 另保存为 `payload_masked_json`（递归脱敏）和 `payload_cipher`（AES 密文）。`payload_cipher` 不属于公开响应；`payload_masked_json` 只在完成递归脱敏后向具备 `integration:youzan:manage` 的管理员作为文本返回，普通 `order:read` 响应该字段为 null，绝不作为原始明文或密文暴露，也不得写入日志或交接示例。

## 5. 人工映射与联调步骤

1. 在 CRM 准备有效 SKU 和已确认权益规则，保存 `shopId + externalSkuId + crmSkuId` 为 ACTIVE；更新时提供 version。
2. 在客户可见范围内选择真实 CRM `customerId`，以 `reason` 保存人工证据，形成 `MANUAL/HIGH` 链接；不得按昵称或手机号自动认领。
3. 仅在本地配置 Mock 密钥，用原始请求体计算开发 HMAC 并调用 webhook；密钥不得打印、写入 fixture 或提交仓库。
4. 调用 Mock `sync` 或 `reconcile`，检查异常队列、重试结果和补偿游标。同步/补偿 header 不是持久化的同步结果快照。
5. 只有映射完整、金额/时间/状态可信且支付确认成功时才发放权益；失败进入异常，不以 202 代替业务成功。

## 6. Mock 签名、原文与密钥边界

- Mock 签名算法为 `hex(HmacSHA256(timestamp + rawBody))`，时间戳为 Unix 秒，允许绝对偏差 300 秒。
- `X-Youzan-Mock-Signature` 和 `X-Youzan-Mock-Timestamp` 是内部测试头，**不是官方签名头或官方 canonicalization 规则**。
- 先对原始请求体验签，再解析 JSON；不要先格式化或重排字段。
- raw 脱敏替换 `mobile/phone/nickname/name/displayName/contactName/address/idCard/buyerName` 为 `***`；完整原文只以 AES 密文保存。
- 密钥、签名、密文不得出现在文档、日志、异常、测试 fixture 或仓库。真实密钥轮换与保管方式仍待 Q11 确认。

## 7. 状态与重试速查

- 原始事件：`RECEIVED → PROCESSED`；分类失败为 `MAPPING_FAILED/CUSTOMER_UNRESOLVED/PAYMENT_MISMATCH`，其他可重试失败为 `RETRY`。
- 异常：`OPEN → RETRYING → RESOLVED`；RESOLVED/DEAD 重试返回 409。`DEAD_LETTER` 字段不证明已有自动死信 consumer。
- 订单：先 DRAFT，满足可信支付后 PENDING_PAYMENT → PAID；同步不得直接覆盖已支付事实。
- 支付：`YOUZAN + PROVIDER_CALLBACK`；人工支付仍为 `MANUAL_REVIEW`。
- 补偿：cursor + nextRetryAt + 外部更新时间共同防止倒退；最多 10 页，`hasMore` 表示仍需继续。

## 9. 实际 Outbox 与事件边界

| event_type | aggregate | payload | topic |
|---|---|---|---|
| `youzan.order.processed.v1` | `youzan`（relay 兼容 `youzan_order`） | `shopId/externalOrderNo/orderId` | `crm.youzan.events.v1` |
| `youzan.sync.issue.v1` | `youzan`（relay 兼容 `youzan_sync_issue`） | `eventId/issueType/status=OPEN` | `crm.youzan.events.v1` |
| `youzan.sync.completed.v1` | `youzan` | `shopId/received/processed/issues` | `crm.youzan.events.v1` |

`TradingMapper.xml` 的 `insertOutboxEvent` 使用 `ON DUPLICATE KEY` 非覆盖写入；并发重复 `sync.completed` 不覆盖已有事件，也不额外形成供应商事件。

`order.paid.v1` 仍使用 `crm.order.events.v1`。这些仅是发布侧契约，不宣称业务 consumer 或 Inbox 消费去重已经实现。
