# 41 企业微信官方客户联系与会话存档对接（P1-2）

## 1. 方案结论与当前边界

企业微信数据按三条独立通道处理：

1. **客户联系官方 API**：员工客户 ID、客户详情、跟进关系、来源和标签；采用“首次/手动全量 + 回调增量 + 每日对账”。
2. **官方客户联系回调**：只负责通知变化，验签解密并落库去重后快速应答，新增/编辑仍重新调用详情 API。
3. **会话内容存档 Finance SDK**：用于聊天正文，与客户资料接口无关；Q10 未确认前继续保持 Mock/Disabled，不采集真实聊天。

本次实现官方客户联系的 HTTP Adapter、运行历史、员工映射、回调验签/解密/幂等和同步页面。没有真实 CorpID、Secret、公网回调地址及企业授权，因此当前只完成官方协议与本地 Mock HTTP 验证，**不宣称生产企微已联通**。

具备 `integration:runtime:manage` 的管理员可在企微页面配置当前租户的官方客户联系和真实会话归档全局开关，保存后无需重启。环境变量仅作为未保存页面配置时的默认值；页面开关不替代 CorpID、Secret、Q10 授权或官方 Finance SDK，会话归档官方 Adapter 未完成时仍保持禁用。

禁止个人微信、非官方 hook、模拟登录，以及按手机号/昵称自动决定 CRM 客户唯一 ID。

## 2. 官方接口依据

实现核对的是企业微信开发者中心以下文档：

| 能力 | 官方文档 |
|---|---|
| access_token | https://developer.work.weixin.qq.com/document/path/91039 |
| 按成员获取客户 ID | https://developer.work.weixin.qq.com/document/path/92113 |
| 批量客户详情 | https://developer.work.weixin.qq.com/document/path/92994 |
| 单客户详情及跟进人分页 | https://developer.work.weixin.qq.com/document/path/92114 |
| 客户变更事件 | https://developer.work.weixin.qq.com/document/path/92130 |
| 回调配置、验签与应答 | https://developer.work.weixin.qq.com/document/path/90930 |
| 会话存档使用前提 | https://developer.work.weixin.qq.com/document/path/91361 |
| 会话存档 SDK | https://developer.work.weixin.qq.com/document/path/91774 |

关键官方限制：

- 每个应用 Secret 独立，token 正常有效 7200 秒，必须缓存并处理提前失效。
- 批量接口 `userid_list` 最多 100 个成员，每页最多 100 条，默认 50 条，必须处理 `next_cursor`。
- 单客户跟进人超过 500 时，`externalcontact/get` 也必须按 cursor 分页。
- 批量结果的 `follow_info` 只返回企业标签和规则组标签 ID，不返回成员个人标签。
- 应用只能获取可见范围内的数据；`external_userid` 不是成员 userid，也不是跨调用方统一的自然人 ID。
- 通过 API 执行的操作不会产生客户联系回调；回调也可能重试、丢失或乱序，必须额外对账。
- 回调 GET 需验签、解密并原文返回 echostr；POST 官方可能因超时重试，接收后应快速应答并异步处理。
- 会话存档不是客户联系 API 的附属能力，且只能拉取最近 5 天数据；需持续按 seq 拉取、msgid 去重，并满足员工告知、外部联系人同意和成员覆盖。

## 3. 实施架构

```text
首次/手工/每日对账
  → WecomTokenService（缓存/刷新）
  → OfficialWecomContactClient
  → batch/get + 完整 cursor
  → WecomContactSyncService
  → crm_wecom_contact + crm_wecom_contact_sync_run

企微回调
  → GET/POST /api/v1/integrations/wecom/callback
  → 签名、AES、receiveid、安全 XML 校验
  → crm_wecom_callback_event（SHA-256 指纹去重）
  → 立即 success
  → 调度异步处理 / 有界退避重试
  → 增改重新拉详情；删除只关闭 follow 关系

会话存档（仍是既有独立链）
  → local Mock 或 Disabled
  → Q10 同意/成员覆盖检查
  → AES 私有对象 + MySQL metadata + DATA_GAP
```

外部 DTO 和 HTTP 只存在 adapter。应用服务保存内部模型，不把企微响应当作订单、客户唯一身份或会话同意证明。

## 4. 数据表与状态机

### V12 新增/扩展

- `crm_wecom_staff_account`：`corp_id + wecom_userid` 映射到 CRM `staff_user_id`。必须明确启用，未知成员不猜身份。
- `crm_wecom_contact`：新增客户名称、头像、类型、性别、可空 unionid、跟进备注/描述、添加来源、state、添加时间、标签 JSON、跟进状态及最近完整同步 run。
- `crm_wecom_contact_sync_run`：FULL/RECONCILE/CALLBACK 运行历史，RUNNING/SUCCESS/ERROR，保存计数、游标和脱敏错误。
- `crm_wecom_callback_event`：事件指纹、类型、成员、外部身份、接收/处理时间、状态、重试次数和脱敏错误。

跟进关系状态：

```text
ACTIVE
  ├─ del_external_contact → DELETED_BY_STAFF
  ├─ del_follow_user      → DELETED_BY_CUSTOMER
  └─ 后续官方详情仍存在   → ACTIVE

DELETED_BY_STAFF / DELETED_BY_CUSTOMER
  └─ 不物理删除历史；新的官方详情可恢复 ACTIVE
```

回调状态：`RECEIVED → PROCESSING → SUCCEEDED`；技术失败进入 RETRYABLE，最多 5 次后 FAILED。未知事件安全完成，不反复阻断队列。

同步运行：同一企业 FULL/RECONCILE 不允许并发。失败回滚本次未提交处理，ERROR 记录单独保存；**失败时不执行缺失关系失效**。

## 5. 全量与对账规则

`POST /api/v1/integrations/wecom/contact-sync`：

- `FULL`：遍历启用员工映射，批量拉取并完整翻页，upsert 客户资料和跟进关系，不因本轮缺失而删除。
- `RECONCILE`：执行相同完整拉取；只有全部员工和全部分页成功后，才把 `last_sync_run_id` 不属于本轮的 ACTIVE 关系标为 `DELETED_BY_STAFF`。
- `CALLBACK`：只更新指定 external_userid 的最新详情，不执行全企业缺失失效。

upsert 不覆盖 `customer_id/link_type/link_reason/created_by`，因此人工身份匹配保留。客户资料同步也不会把 `consent_status` 自动改成 GRANTED；该字段只属于会话存档授权。

定时对账由 `WecomSyncScheduler` 按数据库策略执行：`crm_wecom_sync_policy` 分别控制客户资料和会话归档，支持总开关、间隔及 `next_run_at` 修改。保存后无需重启，原子认领避免多实例重复，失败按类型记录 PARTIAL/ERROR，另一类继续执行。旧 `WecomContactReconcileScheduler` 固定凌晨 cron 已改为默认禁用的 legacy 开关，避免重复对账。

## 6. 回调安全与处理

公开路径只有 `/api/v1/integrations/wecom/callback`；其他内部接口仍需要 CRM 登录、RBAC 和写请求 CSRF。

安全步骤：

1. `msg_signature` 使用 token、timestamp、nonce、Encrypt 按官方排序 SHA-1 规则校验。
2. EncodingAESKey 按 43 位校验，AES/CBC 解密并检查消息长度。
3. 解密 receiveid 必须等于配置的 CorpID。
4. XML 禁止 DOCTYPE、外部实体、XInclude 和实体展开。
5. 解密事件以 SHA-256 指纹唯一落库，重复投递不重复处理。
6. 落库后立即返回 `success`；异步处理避免官方 5 秒超时。

处理事件：`add_external_contact`、`edit_external_contact` 重新拉详情；`del_external_contact`、`del_follow_user` 关闭对应跟进关系；`transfer_fail` 等事件只留处理记录，不伪造继承结果。

## 7. 内部 API 与页面

| API | 用途 | 权限 |
|---|---|---|
| `POST /api/v1/integrations/wecom/contact-sync` | FULL/RECONCILE，幂等键 | `wecom:monitor` + CSRF |
| `GET /api/v1/integrations/wecom/contact-sync/runs` | 最近 50 次运行和脱敏错误 | `wecom:read` |
| `GET/PUT /api/v1/integrations/wecom/sync-policy` | 查询/修改定时策略、两类开关、间隔和下次执行时间 | GET `wecom:read`；PUT `wecom:monitor` + CSRF + 幂等键 |
| `GET/POST /api/v1/integrations/wecom/callback` | 官方 URL 验证与事件接收 | 公开但强制验签/解密/receiveid |
| 既有 `/contacts`、`/contacts/{id}/link` | 客户资料与人工身份匹配 | 原权限与数据范围 |

页面展示客户名称/备注、跟进成员、来源、添加时间、跟进状态、存档同意和人工 CRM 匹配；可手动全量/对账并查看最近状态。客户同步 SUCCESS 与会话存档 DATA_GAP 分开显示，不相互冒充。

## 8. 配置与真实上线交接

仓库只提供非敏感默认值，真实凭证全部由部署环境注入：

```text
WECOM_OFFICIAL_ENABLED=false
WECOM_CORP_ID=
WECOM_SECRET=
WECOM_API_BASE_URL=https://qyapi.weixin.qq.com
WECOM_CALLBACK_TOKEN=
WECOM_CALLBACK_AES_KEY=
```

真实联调前，管理员必须：

1. 创建并启用企业自建应用，配置 CorpID/Secret。
2. 在客户联系“使用范围”和“可调用接口的应用”中完成授权，并限制应用可见范围。
3. 配置企微 userid 与 CRM 员工映射；未知/离职员工停用映射。
4. 配置公网 HTTPS 回调 URL、Token、43 位 EncodingAESKey 和出口 IP。
5. 用真实测试成员/客户验证全量、回调、限流、token 失效和每日对账。
6. 密钥只进密钥管理/部署环境，不进仓库、前端、日志或 fixtures。

## 9. 会话存档继续遵守 Q10

Q10 的存档资质、实际成员范围、客户同意、保存期限、私钥托管/轮换和删除流程未确认前：

- `FEATURE_REAL_WECOM` 不开启真实归档；
- local 继续使用明确虚构的 Mock，其他情况 Disabled；
- 未确认同意或成员未覆盖不存正文，并记录 DATA_GAP；
- 消息列表/Outbox 只含 metadata，正文仅在权限复查后从私有加密对象读取；
- 本次官方客户联系实现不改变上述任何校验。

## 10. 验证要求与证据边界

核心测试包括官方 token/batch HTTP 请求、cursor、回调加解密和坏签名、全量幂等、人工链接保留、重复回调、删除不物理消除历史，以及既有 W01/W02 同意/覆盖回归。

最终验证结果以 CHANGELOG 的实际命令记录为准。Mock HTTP 和本地 MySQL 通过只证明实现符合已核对的官方协议，不代替真实企业授权联调。
