### `crm_notification_delivery` — 每通知每渠道当前投递状态

| 字段 | MySQL 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT UNSIGNED NOT NULL` | 投递主键 |

| `channel` | `VARCHAR(16) NOT NULL` | `IN_APP/WECOM_APP` |
| `status` | `VARCHAR(24) NOT NULL` | `REQUESTED/PENDING/SENDING/RETRY_WAIT/SUCCEEDED/MOCKED/DISABLED/FAILED/UNKNOWN` |
| `attempt_count` | `INT UNSIGNED NOT NULL DEFAULT 0` | 累计开始尝试次数，不等于成功次数 |

| `claim_owner / claim_expires_at` | `VARCHAR(128) / DATETIME(3) NULL` | worker 租约持有者与到期时间，配合 version 防止并发投递 |

| `provider` | `VARCHAR(32) NULL` | 当前实际适配器 `IN_APP/OFFICIAL/MOCK/DISABLED`；不得复用归档配置 |

状态语义：REQUESTED 已随通知和 Outbox 持久化、尚待事件激活；PENDING 可认领；SENDING 已认领执行中；RETRY_WAIT 等待有界自动重试；SUCCEEDED 仅用于 IN_APP 站内可见或 OFFICIAL 官方接口接受；MOCKED 仅表示 Mock 模拟完成，绝不是官方发送成功；DISABLED 表示独立应用消息适配器未启用且未发起官方发送；FAILED 为明确永久失败或重试耗尽；UNKNOWN 表示外部结果不确定，既不是成功也不能当作可盲重试失败。上述投递状态均不表示客户已读。

主状态流为 `REQUESTED → PENDING → SENDING → SUCCEEDED/MOCKED/DISABLED/FAILED/RETRY_WAIT/UNKNOWN`，`RETRY_WAIT → SENDING` 仅用于确认可安全重试的结果。SUCCEEDED、MOCKED、DISABLED、FAILED 不被后台自动改回；UNKNOWN 必须先对账，人工补偿须另留审计。企微应用消息的 Official/Mock/Disabled 选择与会话归档配置、采集开关完全独立，真实 Official 默认禁用。可安全重试时追加新 attempt 并递增 attempt_count，不覆盖既有 attempt。

### `crm_notification_attempt` — 逐次投递最终事实

| 字段 | MySQL 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT UNSIGNED NOT NULL` | 尝试主键 |
| `tenant_id` | `BIGINT UNSIGNED NOT NULL` | 企业/租户隔离，必须与 delivery 一致 |
| `delivery_id` | `BIGINT UNSIGNED NOT NULL` | 所属投递记录 |
| `notification_id` | `BIGINT UNSIGNED NOT NULL` | 通知逻辑对象，便于按通知审计 |
| `attempt_no` | `INT UNSIGNED NOT NULL` | 从 1 开始的 delivery 内累计尝试序号 |
| `channel` | `VARCHAR(16) NOT NULL` | 本次渠道快照 `IN_APP/WECOM_APP` |
| `status` | `VARCHAR(24) NOT NULL` | 最终结果 `SUCCEEDED/MOCKED/DISABLED/RETRYABLE/FAILED/UNKNOWN`，不保存可覆盖的 RUNNING 行 |
| `provider` | `VARCHAR(32) NULL` | 本次实际适配器快照 `IN_APP/OFFICIAL/MOCK/DISABLED`，不随配置后续变化而改写 |
| `provider_message_id` | `VARCHAR(255) NULL` | 官方消息 ID 或明确带 `mock-` 前缀的模拟 ID；MOCKED 不得冒充官方回执 |
| `error_masked` | `VARCHAR(512) NULL` | 本次稳定脱敏错误，不含正文、凭证或上游完整响应 |
| `trigger_type` | `VARCHAR(24) NOT NULL` | `INITIAL/AUTOMATIC/MANUAL/LEASE_RECOVERY` |
| `actor_user_id` | `BIGINT UNSIGNED NULL` | 手工重试操作人；系统触发为空 |
| `created_at` | `DATETIME(3) NOT NULL` | 最终结果记录时间 |

唯一键 `uk_notification_attempt_no`：`tenant_id + delivery_id + attempt_no`。通知历史索引 `idx_notification_attempt_notification`：`tenant_id + notification_id + id`。`delivery_id` 与 `notification_id` 分别引用对应表，禁止级联删除历史。

每次投递决策或执行完成后追加一条最终 attempt，包括 DISABLED 的明确未调用结果；不得先写 RUNNING 再覆盖。SUCCEEDED、MOCKED、DISABLED、RETRYABLE、FAILED、UNKNOWN 均为不可覆盖历史，重试必须新增 attempt_no。delivery 当前状态、attempt_count、租约与最后错误和最终 attempt 在同一 MySQL 事务追加/更新。UNKNOWN 必须告警并对账，不得直接按普通失败盲重发；MOCKED 只能解释为模拟适配器完成。

回滚边界：先在配置侧选择 Disabled 并停止 notifier 认领，等待或对账在途 Official 调用；无历史数据且获批准时可按 `crm_notification_attempt` → `crm_notification_delivery` → `crm_notification` 顺序回滚新增结构。已有通知或投递历史时不得用删表、删行或重置 attempt 代替业务回滚，须保留审计与对账依据。

### 企微通知成员映射（V40）

`crm_wecom_staff_account` 新增 `message_enabled`（独立允许应用通知，默认 1）和 `version`（映射维护乐观锁，默认 0），并以 `tenant_id + corp_id + staff_user_id` 唯一键防止同一员工多义映射。原 `enabled` 仍只控制归档/客户同步，不能替代通知授权。通知反查仅接受 `message_enabled=1` 且唯一的成员 ID；新增映射默认 `enabled=0`，不会自动扩大归档采集范围。

| `status` | `VARCHAR(16)` | `ACTIVE/DISABLED`；停用后公开读取不可见 |
| `disable_reason / disabled_by / disabled_at` | `VARCHAR(1000) NULL / BIGINT UNSIGNED NULL / DATETIME(3) NULL` | 脱敏停用理由、操作者与 UTC 时间 |
| `created_at / updated_at / version` | `DATETIME(3) / BIGINT UNSIGNED` | UTC 创建、更新时间及停用乐观锁 |

`trg_h5_card_snapshot_guard` 只允许 ACTIVE → DISABLED 的版本与状态变化，标题、摘要、正文、项目、客户、员工与分享键均不可覆盖。链接和封面不保存为可变业务事实，而是由服务端根据受信侧边栏 Origin 派生。公开读取只返回项目名称与公开内容，不提供公开列表。

### `crm_wecom_h5_card_usage` — 复制与 SDK 结果日志

字段包括 `id、tenant_id、card_id、employee_id、customer_id、send_status、client_result、send_time、idempotency_key、created_at`。`send_status` 为 `COPIED/SDK_SUCCESS/SDK_FAILED/SDK_UNKNOWN`；客户端结果脱敏，成功不代表客户已读。唯一键为 `tenant_id + idempotency_key`，另有卡片与员工时间索引。

结果只能由卡片所属员工针对原客户记录；停用后仍允许补记已经发生的真实 SDK 结果。`trg_h5_card_usage_no_update/no_delete` 保证只追加。V47 回滚删除两张 H5 表及三个触发器，不影响项目、客户、AI 回复或快捷话术表；已有真实分享历史不得用删表代替业务处置。


## 企微媒体资产与下载 Worker（V49）

### `crm_wecom_media_asset` — 消息媒体元数据与恢复状态

| 字段 | MySQL 类型 | 说明 |
|---|---|---|
| `id / tenant_id / message_id / asset_index` | `BIGINT UNSIGNED / INT UNSIGNED` | 主键、租户、已授权消息与消息内媒体顺序；唯一键为租户 + 消息 + 顺序 |
| `sdk_file_id` | `TEXT` | 企微官方媒体文件 ID，只用于后台分片下载，不返回前端或公开页 |
| `media_kind` | `VARCHAR(32)` | 来源节点，如 image、voice、video、emotion、file 或嵌套消息类型 |
| `md5sum / file_size` | `VARCHAR(64) NULL / BIGINT UNSIGNED NULL` | 企微声明的完整性校验值与字节数；下载完成后逐项复核 |

| `status` | `VARCHAR(16)` | `PENDING/DOWNLOADING/RETRY/STORED/FAILED`；仅 STORED 可授权读取 |
| `object_key / content_sha256 / actual_size` | `VARCHAR(512) NULL / CHAR(64) NULL / BIGINT UNSIGNED NULL` | 私有对象 Key、实际内容 SHA256 与字节数，大二进制不写 MySQL |

V49 回滚只删除媒体资产表，不影响已归档消息、客户或 H5 卡片；已有媒体对象应按生命周期策略处理，不能用删表代替内容处置。


## 企微消息撤回与乱序补全（V50）

### `crm_wecom_message` 的 V50 变更

新增可空 `recalled_at DATETIME(3)` 与 `recall_message_id VARCHAR(192)`，分别表示官方撤回生效 UTC 时间和控制消息 ID。`status` 仍表示 STORED/UNMATCHED 客户匹配状态，不与撤回混用；`content_object_key`、原始正文、发送时间、同意快照均不删除或覆盖。

只有员工、external_userid、发送方类型均与原消息一致时才允许撤回。更新使用 `recalled_at IS NULL + version` 防止重复覆盖；已撤回消息仍受当前同意、归档成员与客户数据范围控制。

### `crm_wecom_recall_event` — 撤回控制事件

| 字段 | MySQL 类型 | 说明 |
|---|---|---|
| `id / tenant_id / corp_id` | `BIGINT UNSIGNED / VARCHAR(96)` | 主键、租户与企业隔离 |
| `recall_message_id / original_message_id` | `VARCHAR(192)` | 撤回控制消息 ID 与 revoke.pre_msgid；分别有唯一约束 |
| `recall_seq` | `BIGINT UNSIGNED` | 撤回控制消息的归档序号，用于缺口补全 |
| `external_userid / staff_user_id / sender_type` | `VARCHAR(192) / BIGINT UNSIGNED / VARCHAR(32)` | 撤回会话、员工与发送方一致性校验 |
| `occurred_at` | `DATETIME(3)` | 官方撤回发生时间 UTC |
| `status` | `VARCHAR(24)` | `PENDING_ORIGINAL/APPLIED`，支持先撤回后到原消息 |
| `original_message_ref` | `BIGINT UNSIGNED NULL` | 补全后的内部消息引用，可空外键 |
| `created_at / applied_at / version` | `DATETIME(3) / BIGINT UNSIGNED` | 首次接收、补全时间 UTC 与乐观锁 |

同一撤回事件重放不重复更新或发布；原消息不存在时保存 PENDING_ORIGINAL 并记录 `RECALL_ORIGINAL_PENDING` 缺口，原消息合法入库后补全为 APPLIED 并关闭对应缺口。实际生效时追加 `wecom.message.recalled.v1` Outbox 事件，payload 只含 messageRef、recalledAt、recallMessageId，不含正文。

V50 回滚先删除撤回事件表，再移除消息撤回字段，不影响媒体资产、原消息正文或既有内容对象。已有撤回事实不应以结构回滚代替业务处理。

## P3 企微运营分析口径（V53，无表结构变更）

V53 不新建事实表，复用 `crm_quick_reply_usage`、`crm_ai_reply_suggestion`、`crm_appointment`、`crm_appointment_history`、`crm_order`、`crm_payment_txn` 和 `crm_customer`。所有聚合显式带租户、UTC 半开时间窗口、当前客户数据范围与可选员工条件，不使用 Redis 作为统计账本。

- 话术日志按 `send_status` 分别统计复制、SDK 成功/失败/未知，复制不计入 SDK 成功率分母；`ai_suggestion_id` 仅由既有已采纳候选校验链写入。
- AI 采纳率使用期内创建候选的当前状态，不能把复制、SDK 成功或客户已读冒充采纳；Mock 候选单独计数。
- 到院率以真实 CONFIRMED 历史所属预约为分母，以确认后且期末前的 CHECKED_IN 为分子，不把计划到院当成实际到院。
- 复购统计只使用有效订单的 CONFIRMED 支付事实，同一订单多个流水去重；期内至少两笔不同已支付订单才计入多次付费客户，不按客户+聊天时间窗推断因果。
- 没有可靠回执的 MESSAGE_READ_RATE/H5_OPEN_RATE/CHAT_CAUSAL_ATTRIBUTION/QUICK_REPLY_BUSINESS_OUTCOME 只返回不支持标记，不写 0 或虚构统计事实。
