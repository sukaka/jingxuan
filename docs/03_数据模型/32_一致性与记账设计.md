# 32 核心记账、幂等、并发和对账算法

## 1. 余额的权威计算
每个项目 entitlement 的余额：
```
available = SUM(entitlement_ledger.delta_count) WHERE entitlement_id = ?
```
若 `available_count` 缓存快照存在，则更新必须同一个 MySQL 事务内进行，定期夜间全量核验与账本 sum 一致；不一致自动冻结有风险权益并创建风控问题单，不允许后台直接手改快照。

## 2. 支付成功后发权益的事务伪代码
```text
validate payment proof or verified provider callback
BEGIN
  INSERT idempotency(scope='payment.confirm', key=providerTradeNo) unless exists
  SELECT order WHERE id=? FOR UPDATE
  ASSERT order not previously paid and payment amount matches business rule
  INSERT payment_txn CONFIRMED
  UPDATE order status=PAID, paid_fen=...
  FOR EACH order_item resolved snapshot project:
    INSERT entitlement (project, grantCount, availableCount)
    INSERT entitlement_ledger(GRANT, +grantCount, unique source)
  INSERT outbox_event(payment.confirmed)
COMMIT
```
回调重复返回首次结果；多次支付/部分支付应先统一设计支付聚合状态，不能用“订单付过就拒绝所有合法补款”。

## 3. 医院核销的事务伪代码
```text
ASSERT principal has INSTITUTION_REDEEM and appointment.institution_id in currentPrincipal.institutions
BEGIN
  INSERT idempotency_record(scope='redemption.post', key=Idempotency-Key)
  SELECT appointment WHERE id=? FOR UPDATE; ASSERT status CHECKED_IN/SERVICE_DONE
  SELECT entitlement WHERE id=? FOR UPDATE
  ASSERT entitlement.customer == appointment.customer
  ASSERT sku/project/institution permitted and within valid dates
  ASSERT availableCount >= requestedCount >= 1
  INSERT redemption POSTED(verified_by_institution_user_id=principal.id)
  INSERT entitlement_ledger(REDEEM, -count, source=redemptionId)
  UPDATE entitlement available_count -= count, version +=1
  UPDATE appointment status=REDEEMED or PARTIALLY_REDEEMED
  INSERT outbox_event(entitlement.redeemed)
COMMIT
```
失败回滚所有表；并发从未允许负可用次数；取消核销只能新建冲正记录和补偿流水；不可 `DELETE` 原核销。

## 4. 退款
现金支付通道确认 `SUCCEEDED` 是执行退款成功记账的条件。回收项目权益时：对 refundItem 按 entitlement 锁，确认可用次数 >= 回收次数，写负 `REFUND_REVOKE` 流水，累加成功退款和实际付款退回记录。如果商家/支付渠道退款成功但权益因竞争不足，进入**财务业务补偿异常**，不要将支付成功记录偷偷改为失败；需要事前预留/冻结权益方案或统一事务策略设计。客户已完成服务发生争议退款要人工制定补偿规则，不能逆造核销事实。

## 5. 金额分摊示例
订单实际收款 3,311 元 = 331100 分，套餐有多个不同子项目，不能直接除以总次数当作每次值。推荐在购买时按照财务确定的项目权重 `w_i` 分摊：
1. 计算理论值 `raw_i = total_fen * w_i / sum(w)`（高精度 Decimal）；
2. 每项先 `floor` 到整数分；
3. 剩余 `total_fen - sum(floor)` 分按照小数余数从大到小（同分固定 projectId 升序）逐分补足；
4. 保存分摊规则版本、项目权重和结果快照；满足 `sum(allocated_amount_fen)=paid_fen`；
5. 核销金额按该项目权益已分配金额再分摊到每次消费，使用同样余数算法，并记录原交易与分摊版本。

## 6. 机构佣金与结算
结算基数必须配置（基于实付/核销/净核销/医院代收等）且 Q04、Q05 签字后启用。线上线下、点评佣金、保投产、保证金按单独规则版本计算。`settlement_line` 保存**核销ID+对应规则快照+分摊金额**，月结批次或次卡次结均不可重复对同一核销结算（建议增加业务唯一确认约束）。差错通过账单更正行、调整行反映，不能删除历史已付流水。

## 7. 自动对账任务（最少每天）
- 每个权益：`ledgerSum = availableCount`；若不同报警。
- 每个订单：`sum payment_confirmed - sum successful_refund = 净现金流`（按收款方区分）。
- 每条正式核销：存在唯一负权益流水；每条冲正有原值/反值关系。
- 每个成功退款：存在唯一可信支付退回结果与权益回收决策记录。
- 每张结算单：明细总额、佣金、应结、已付款存在业务等式与来源凭证。
- 所有异常生成风险台账记录 `risk_case`（建议后续增表）并记录日期/影响金额/处理人/关闭凭证。

## 8. 并发专项测试
同一权益剩 1 次，两个医院操作员同时请求各核销 1 次；预期仅一个成功，另一个409，账本最终余额0，总核销1。相同幂等键重试100次返回同一资源ID。支付回调乱序/重复后权益不重复。审计日志及 Outbox 与交易一起提交。
