# 33 动态字典、可编辑列表与主数据治理

## 1. V2.0 提出的“别再写死”的问题
以下必须由系统管理员在 **系统配置 → 基础字典/列表配置** 维护：城市、机构业务类型、机构性质、商户等级、结算方式、客户状态、客户来源、客户渠道、订单类型、活动名称、沟通方式、任务类型、退款原因、素材类型。每项至少 `code、label、sort、enabled、createdBy、updatedBy、version`。

## 2. 字典生命周期
`DRAFT → ACTIVE → INACTIVE → ARCHIVED`。有历史引用的字典值不能物理删除；“修改 label”不影响存储的 `code`；修改 `code` 必须走主数据迁移而非普通编辑。每次修改 Audit + Kafka cache invalidation，Redis 通过版本键重建缓存。下拉 UI 默认不展示停用项，但历史详情正常显示“已停用”。

## 3. 业务实体编辑分类
| 实体 | 允许修改 | 禁止直接修改 |
|---|---|---|
| 客户 | 姓名、昵称、城市、标签、备注、跟进 | 归属历史、已成交时点归属 |
| 跟进 | 误录更正、下次时间、摘要，可软删除未用于审核的记录 | 企业微信已归档原始聊天消息 |
| 订单 | 草稿价格/项目、非核心活动归属 | 付款后实付、成交时SKU权益快照 |
| 套餐 | 创建未来版本、停售规格 | 已售版本的历史权益 |
| 医院 | 一般介绍、医生、仪器、案例；重要字段走审批 | 已审生效的合同/佣金/银行历史 |
| 预约 | 机构确认前时间/机构等；完成前按条件改期 | 完成/核销后原历史 |
| 核销 | 提交前草稿 | POSTED 历史，只能冲正 |
| 退款 | 未审批申请金额/原因 | 成功退款事实 |
| 素材 | 草稿/已拒绝重新修订 | 已审核对外版本被静默覆盖 |
| SKU | 新建编码/未来价格版本/停用 | 已售 SKU 定价历史 |

## 4. 主数据编号规则
`customer_no`, `institution_no`, `project_code`, `package_code`, `sku_code`, `campaign_code` 全部稳定且唯一，名称可修改但编码不可复用。推荐 `SKU = 分类码-项目码-规格码-销售渠道码`，**仅为推荐模板**；最终规则需运营拍板。不允许把商品中文名称当作唯一匹配有赞商品的键，必须使用外部 SKU ID 映射关系。

## 5. 业务编辑授权与审计
每个 PATCH 要求并发版本号/If-Match；关键字段提供 before/after；软删除需 `deleted_at,deleted_by,delete_reason`（基线仅部分表具 deleted，P0 领域 PR 必须补足）。导入旧表时允许存原字典原名与标准字典码的映射，待确认后再批量更新。
