# 90 工程目录与代码实现约定（给 Codex / Claude Code）

**目标**：在保持 V2.0 原型业务功能的同时，构建可维护、可测试、可部署的模块化单体，而非把 HTML 中的所有逻辑原样搬到后端。

## 1. 推荐 Monorepo 目录

```text
whale-crm/
├── AGENTS.md                     # 直接复制交付包根目录 AGENTS.md
├── README.md
├── docs/                         # 放置本交付包原有 docs 和验收文档
├── infra/
│   ├── compose/                  # 开发中间件及本地观测组件
│   ├── mysql/                    # MySQL 初始化与排障，不替代 Flyway
│   └── observability/            # Grafana/Prometheus/OpenTelemetry
├── apps/
│   ├── crm-web/                  # Vue3 + TS + Vite + Element Plus
│   │   ├── src/api/              # 生成/封装类型化 OpenAPI Client
│   │   ├── src/views/            # 页面，仅页面级编排
│   │   ├── src/components/       # 表格/编辑弹窗/通用表单
│   │   ├── src/router/           # 按权限路由，后端仍二次鉴权
│   │   ├── src/stores/           # Pinia 缓存 UI 状态，不放权威余额
│   │   └── src/utils/

│   │   │   ├── customer/         # 客户、身份、转交、积分、跟进

│   │   │   └── integration/      # 有赞和企微适配端口（port）
```

如团队暂不需要 `integration-worker` 独立进程，可先作为 `crm-api` 中独立适配模块/调度任务。**同一个业务事务不得跨多个服务和数据库。**

## 2. 单业务模块内的固定分层

```text
customer/
  api/CustomerController.java
  api/dto/CreateCustomerRequest.java
  application/CustomerApplicationService.java
  domain/Customer.java
  domain/CustomerRepository.java
  infrastructure/MybatisCustomerRepository.java
  infrastructure/mapper/CustomerMapper.java
  security/CustomerScopePolicy.java
```

- Controller：只做鉴权入口、校验、入参映射、HTTP 状态；禁止直接写核心 SQL。
- Application：事务边界、权限语义、流程协调、幂等控制、审计与 Outbox。
- Domain：业务规则及状态机，不依赖 HTTP/Kafka/外部平台 DTO。
- Infrastructure：MyBatis、Redis、外部 Adapter、文件存储实现。
- 跨模块查询：定义只读 QueryService 或内部端口，避免直接偷调其他模块 Mapper。

## 3. API 与前端约定

统一 API 前缀 `/api/v1`。列表返回 `items/total/page/size`，所有排序字段白名单，`size<=100`，使用规范化日期（UTC 时间戳 + 用户时区展示）与金额 `xxxFen` 整数值；**接口不可接受客户端传来的 `tenantId`、`verifiedBy`、`createdBy` 作为可信事实**。

推荐响应：
```json
{"code":"OK","data":{"id":"12345","version":1},"requestId":"01J..."}
```

错误示例：
```json
{"code":"ENTITLEMENT_INSUFFICIENT","message":"可用服务次数不足","requestId":"01J...","details":{"entitlementId":"42"}}
```

| HTTP | 适用场景 | 要求 |
|---|---|---|
| 400 | 字段类型/格式无效 | 统一 Validator，不在前端私自决定合法性 |
| 401 | 未登录/Token 过期 | 不泄露是否存在某客户 |
| 403 | 有身份但没有访问权限 | 不泄露其他机构财务或聊天数据 |
| 404 | 资源不存在或不可见 | 访问敏感资源优先避免资源枚举 |
| 409 | 状态冲突/乐观锁失败/额度竞争 | 客户端刷新，禁止盲目自动重试业务写入 |
| 422 | 业务配置未确认 | 返回明确 `PENDING_BUSINESS_RULE` 与 Qxx 标识 |
| 429 | 超出限流 | Retry-After 或固定限流提示 |

前端应提供：**搜索、分页、筛选、详情、创建、修改、操作确认、失败提示、操作日志、空态、加载中**，操作可见性跟随角色；但任何菜单隐藏都不能替代后端鉴权。DTO 类型从 OpenAPI 生成，不手工多处维护相同字段。

## 4. 表单修改与并发

每张可编辑业务表提供 `version` 乐观锁。更新时使用 `WHERE tenant_id = ? AND id = ? AND version = ?`；成功 `version+1`，影响行数为 0 返回 409。

对机构佣金/银行/合同这类敏感字段，不能调用普通 `/institutions/{id}` 更新直接生效，必须走 `/change-requests`，审批通过后才在同一 MySQL 事务中比较 `baseVersion` 和写入新值、日志、Outbox。

已有成功支付或正式核销、退款的财务事实不得实现“编辑已完成记录”的通用 CRUD；对外暴露退款/冲正/补正业务动作 API。

## 5. 分阶段验收命令（模板，不代表已执行）

```bash
mvn -pl apps/crm-api -am verify
npm --prefix apps/crm-web run typecheck
npm --prefix apps/crm-web run lint
npm --prefix apps/crm-web run test
npm --prefix apps/crm-web run build
python -m pytest apps/ai-worker/tests
```

每个阶段还需在容器化 MySQL、Redis、Kafka 上运行 Testcontainers 集成测试，并在交付说明中明确执行结果、日志片段与未运行项目。没有真实第三方账号时，必须以 Mock + 固定 fixture 验证，并在 UI 标注“未对接”。

## 6. 数据迁移与发布

- Flyway 迁移文件只能追加，已经在测试/生产使用过的迁移不得原地改写。
- 数据库结构改变先执行 expand，再灰度应用，再迁移历史数据，最后收缩旧字段（contract）。
- 回滚优先选择应用回滚和补偿性迁移，不依赖自动删除已产生的财务数据。
- 每个任务卡结束同步更新 `contracts/`、`docs/`、测试用例、变更记录与遗留问题。
