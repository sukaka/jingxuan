# 通知与企微应用消息

## 边界与事务

`com.whale.crm.notification` 只负责逻辑通知、渠道投递和企微应用消息，不读取企微会话归档运行开关。其他领域通过 `NotificationRequestService.request` 创建通知；该方法使用 `Propagation.REQUIRED`，与调用方业务写处于同一 MySQL 事务。

逻辑通知包含 `tenantId`、`recipientUserId`、`notificationType`、`title`、`contentMasked`、`sourceType/sourceId`、`dedupeKey`、`deepLink`、`createdAt/readAt`。调用方必须传入已脱敏正文；审计只记录状态和版本，不记录标题或正文。通知去重键在租户和接收人内唯一，同键不同逻辑内容返回 409。

请求在同一事务中写入通知、各渠道 `REQUESTED` 投递和 Outbox。事件契约固定为：

- `event_type=notification.requested.v1`，`event_version=1`；
- `aggregate_type=notification`，Topic `crm.notification.request.v1`；
- payload 仅含 `{"notificationId": 123}`，不得加入标题、正文或接收人标识；
- 消费组 `crm-notification-request`，先写 `crm_inbox_event` 再把投递激活为 `PENDING`；非法契约经有限重试进入 `crm.dlq.notification.request.v1`。

## 投递状态机

| 当前状态 | 允许动作与下一状态 |
| --- | --- |
| `REQUESTED` | 有效 Kafka 事件消费后为 `PENDING` |
| `PENDING` / `RETRY_WAIT` | worker 通过版本号和租约原子抢占为 `SENDING` |
| `SENDING` | 官方明确成功为 `SUCCEEDED`；Mock 为 `MOCKED`；禁用为 `DISABLED`；限流/可重试错误为 `RETRY_WAIT`；永久错误为 `FAILED`；结果不确定为 `UNKNOWN` |
| `SENDING` 且租约过期 | 追加 `UNKNOWN` 尝试，不自动重发 |
| `RETRY_WAIT` | 到期后重新抢占；超过自动重试上限转为 `FAILED` |
| `FAILED` / `DISABLED` | 管理端凭版本号和幂等键手工重试为 `PENDING` |
| `UNKNOWN` | 永不自动重试；管理端核实后填写原因，凭版本号和幂等键手工重试为 `PENDING` |

`SUCCEEDED` 和 `MOCKED` 不允许重试。`MOCKED` 明确代表合成结果，不能展示或记作真实企微发送成功。每次最终投递结果追加到 `crm_notification_attempt`；通知逻辑字段及最终尝试由数据库触发器禁止覆盖或删除。

## API 与权限

- `GET /api/v1/notifications`：只查询当前用户的通知，支持 `unreadOnly`、`notificationType` 和分页。
- `GET /api/v1/notifications/unread-count`：只统计当前用户未读。
- `POST /api/v1/notifications/{id}/read`：请求体必填且必须包含 `version`（例如 `{"version":0}`）以校验客户端版本，空请求体或缺失版本返回 400；必须携带非空白 `Idempotency-Key`，权限 `notification:read`。响应同时保留请求渠道快照 `channels` 和实际渠道摘要 `deliveries`。
- `GET /api/v1/notification-deliveries`：管理端按通知、接收人、渠道和状态查询，权限 `notification:delivery:read`。
- `POST /api/v1/notification-deliveries/{id}/retry`：请求体包含 `version`，`UNKNOWN` 必须同时包含非空白 `reason`，必须携带非空白 `Idempotency-Key`，权限 `notification:delivery:retry`。

所有写接口由全局双提交 CSRF 过滤器保护。本人接口始终使用认证主体的 `tenantId/userId`，不能通过参数切换接收人；管理查询也必须显式带租户条件。已读和手工重试使用乐观锁、同请求幂等回放及追加审计。

## 独立企微应用消息配置

| 环境变量 | 含义 | 默认值 |
| --- | --- | --- |
| `WECOM_MESSAGE_MODE` | `DISABLED` / `MOCK` / `OFFICIAL` | `DISABLED` |
| `WECOM_MESSAGE_CORP_ID` | 应用消息企业 ID | 空 |
| `WECOM_MESSAGE_SECRET` | 应用消息独立 Secret，仅环境注入 | 空 |
| `WECOM_MESSAGE_AGENT_ID` | 应用 Agent ID | `0`，Official 下无效 |
| `WECOM_MESSAGE_API_BASE_URL` | 官方 API 地址 | `https://qyapi.weixin.qq.com` |
| `NOTIFICATION_KAFKA_ENABLED` | 通知消费者开关 | 本地 `false`，生产 `true` |
| `NOTIFICATION_WORKER_ENABLED` | 投递 worker 开关 | 本地 `false`，生产 `true` |

Router 不读取归档的 `WECOM_OFFICIAL_ENABLED` 或运行时归档开关，也不会在 Official 失败时降级为 Mock。Token 独立缓存并在过期前刷新，收到 `40014/42001` 只刷新重试一次；`45009`、HTTP 429 和服务端错误进入有界退避。网络超时、响应无法解析或 worker 崩溃后的结果一律为 `UNKNOWN`，不得自动当作失败重发。

发送前通过 `crm_wecom_staff_account` 按 `tenantId + recipientUserId + corpId` 反查人工确认的成员 ID；缺失、多义或 `message_enabled=false` 时永久失败且不发 HTTP。该表的 `enabled` 仅表示是否参与客户同步，`message_enabled` 独立控制应用通知。

V40 增加 `message_enabled/version` 和每员工每企业唯一约束。管理员通过 `GET /api/v1/notification-settings/wecom-mappings` 查询，POST 新增、PUT `/{id}` 修改；写操作要求 `notification:delivery:retry`、CSRF、幂等键、理由和审计，PUT 同时校验 version。新增映射默认不参与归档同步，已有通知和投递历史不被修改。

V28 对应 `db/migration/V28__notification_delivery.sql`，回滚为 `db/rollback/V28__notification_delivery_rollback.sql`；回滚先删触发器，再按 attempt、delivery、notification 顺序删表。

## V37 批量标签执行结束通知

`BatchTagJobExecutionService` 在每次任务最终完成事务中，为可加载的原请求人创建 `notificationType=BATCH_TAG_JOB_FINISHED` 的逻辑通知：

- `sourceType=BATCH_TAG_JOB`，`sourceId` 为任务 ID；`deepLink=/customers/batch-tag-jobs?jobId={jobId}`。
- `dedupeKey=batch-tag-job:{jobId}:{attemptCount}`，同一执行次数不重复创建；重试或租约恢复形成新的执行次数。
- 脱敏正文只含任务编号、最终 SUCCEEDED/PARTIAL_FAILED/FAILED 状态及实际变更、无需变更、跳过、失败计数；请求渠道仅 `IN_APP`，不会因 V37 自动发起企微应用消息。
- 通知与任务完成共用 V28 `notification.requested.v1`、payload `notificationId` 和现有投递/尝试状态机。没有新增 `batch.tag.*` 或 V33 时间线事件，事件 Schema 无需增加 event_type。
- 通知创建或投递不能反向修改任务事实；站内已读也不表示客户或企微成员已读。
