# 52 非功能需求与初始 SLO 建议

> 下列数值是**初始工程目标，尚非用户批准的合同 SLA**；需依据真实客户数、日消息量、机构数、服务器预算做压测。

## 1. 性能目标
- 普通读 API p95 < 300ms（不含外部同步/AI推理），列表在限制分页下 p95 < 500ms；关键交易确认 API p95 < 800ms（仅内部 MySQL 事务）。
- 前端客户详情打开首屏 < 2s（典型办公网络）；聊天/报表分页加载，不一次返回无限消息。
- 有赞/企微异步同步延迟明确标示：正常情况下目标 5min 内更新；外部 API 限流/不可用时显示真实最后同步时间，告警。
- AI 消息摘要是异步任务，不能阻塞管家建单/机构核销；模型调用超时有失败态和重试限制。

## 2. 容量规划的参数化模型
设客户 N、每日企微消息 M、订单日增长 O、每单子项目数 P、核销日次数 R、文件日上传 MB。建容量表，MySQL 指数基于 `N/O/R`，对象存储基于媒体总量，Kafka 消息基于 M 与系统事件。首阶段以开发/压测假设值来确定索引与分区，用户给真实规模后重新估算。

## 3. 可用性和恢复目标
建议关键 CRM 工作时段月可用 99.9%（需资金与团队确认）。初期建议 RPO <= 15分钟、RTO <= 4小时，必须实际做数据库 PITR 与文件恢复演练才能承诺。Kafka 消费积压不应导致核心事务不可用；反过来 MySQL 不可用时禁止以缓存确认核销。

## 4. 数据质量目标
- 资金/权益账本与快照一致性100%，外部订单重复记账0，权限越权数据泄露0。
- 主要字段完整度、SKU映射率、客户身份匹配率、医院核销来源完整率、会话存档覆盖率可量化日看板。
- `source_system + external_order_no` 重复冲突数、未解决退款/结算差异、过期资质仍可预约属于高优先告警。

## 5. 容错策略
Kafka不可用→Outbox积压+告警而不是放弃提交已成功订单；Redis不可用→降级DB查询与速率保护；外部供应商不可用→原数据保存+人工处理/轮询补偿；AI不可用→人工管家继续使用 CRM。

## 6. 观测与成本
监控 MySQL慢查询/锁竞争、Kafka lag、Redis memory/evictions、AI每千会话成本、MinIO用量/扫描失败、订单同步缺口、会话归档连续性、导出频率、权限拒绝和异常审批操作。每月复盘容量估算与权限配置。
