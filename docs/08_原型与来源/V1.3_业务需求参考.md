# 医疗会员 CRM + 企业微信 + AI 智能管家系统

**整合需求说明书（V1.3）**  
**编制日期：2026-10-10**  
**状态：开发需求初稿 / 待业务确认**  
**需求来源：**① 当前 CRM 建设讨论；②《管家部填表必填事项及规范——更新26.8.24》；③客户信息表（23字段）截图；④机构/产品组合/子项目/合作渠道/日跟进/售卖/核销/管家业绩/商务业绩截图；⑤客户-达人-管家-医院-财务完整业务流程图  
**范围边界：**仅接入企业微信官方能力，不接入个人微信；涵盖客户、会员、订单、医院、核销、退款、回访与 AI 辅助运营。

> **文档目的**：把原有四张智能表格的实际使用流程迁移为可审计、可扩展的 CRM 正式业务流程，并增加会员余额管理、医院履约、退款、企业微信消息归档及 AI 智能管家能力。本文区分“原规范要求”“系统改造建议”“待确认业务规则”，避免将建议误作既有制度。

## 1. 核心目标与建设原则

### 1.1 业务目标

1. 老板或授权主管能查看每名客户的累计成交、实付、退款、购买项目、剩余次数/金额、历史服务医院与管家跟进情况。
2. 管家打开客户详情即可知道：最近聊了什么、是否预约、是否到院、是否存在未核销服务、下一步何时回访。
3. 原有“客户信息表 → 日沟通情况表 → 售卖登记表 → 订单核销明细表”关联流程平滑迁移，减少手工填报和漏报。
4. 企业微信沟通在符合开通、授权和客户同意等条件下进入 CRM，由 AI 抽取意图与待办，但不得未经核验自动确认成交、核销或退款。
5. 核销次数、未核销金额、退款金额可核算、可追溯、可对账；历史更正必须有记录。

### 1.2 实施原则

- **业务事实优先**：订单支付、项目核销和退款状态以业务凭证及正式记录为准；聊天仅作为线索和证据。
- **保留操作习惯**：管家仍然只需少量字段录入，手机端有“收集表”式表单，系统自动带出客户姓名、管家、订单信息。
- **主键不依赖手机号**：以 `customer_id` 为永久主键；手机号可空；企业微信 `external_userid` 是客户身份映射的一部分，不代表唯一的业务主键。
- **变动有流水**：权益发放、扣减、冲正、退款回收均追加流水；禁止直接改余额字段。
- **事件幂等**：成交触发、同步消息、核销重试等操作必须去重，避免同一事件生成多笔订单或重复扣次数。
- **范围明确**：不使用个人微信外挂、模拟登录、消息爬取。第三方医院接口与模型服务按实际条件分阶段接入。

## 2. 原 Word 四张核心表的需求落地

| 原表及操作时机 | 原规范中的动作 | CRM 模块及升级后的处理 |
|---|---|---|
| 1-客户信息表：新增客户时 | 先建档，再做沟通记录；手机号选择带出姓名、来源 | 客户中心。新建客户生成唯一编号；可先仅录昵称，后补手机号；自动关联企业微信客户身份和所属管家 |
| 5-客户日沟通情况表：每次沟通后 | 同一客户每次新增一行；记录沟通内容、方式、下一步；成交日期可能触发销售记录 | 沟通时间线。企业微信可归档消息自动形成原始记录，AI 提议沟通摘要，管家确认；非自动渠道可手动新增 |
| 6-售卖登记表：客户成交时 | 带出姓名电话/管家/创建人/下单日期；填写订单号、项目、金额、次数和凭证 | 订单中心。成交事件生成**待完善订单草稿**，确认支付及订单字段后生效；自动汇总成交与权益 |
| 10-订单核销明细表：每次到店 | 从售卖记录触发新核销行；填核销时间、项目、金额、次数；自动汇总剩余 | 到院核销中心。明确关联订单项与医院；使用一次性核销提交操作，生成核销流水；更新剩余次数、已/未核销金额 |

**原规范保留**：先建档、姓名关联带出、每次沟通单独新增、成交后补齐订单信息、每次核销独立一笔记录、日终检查缺漏。

**系统升级**：原来用“成交日期不为空”触发正式销售、或用复选框的“取消再勾选”创建核销记录，容易出现重复和误操作；新系统将两者改为显式的**成交确认/生成订单草稿**与**新增核销/确认核销**动作，保证界面仍快捷，但后台具备幂等校验和权限审批。

## 3. 业务角色、权限与入口

| 角色 | 权限范围 |
|---|---|
| 系统管理员 | 组织、角色、配置、企业微信集成；原则上不默认拥有所有敏感聊天全文的查看权 |
| 老板/经营负责人 | 全局经营报表和授权范围内客户资料、资金与项目进展 |
| 管家主管 | 其管理团队客户、漏填告警、任务分配、核销/退款异常复核 |
| 专属管家 | 自己负责的客户、沟通、预约、跟进、待补录订单、提交核销申请 |
| 财务人员 | 实付确认、退款执行、订单财务校验和对账；敏感聊天按需最小授权 |
| 运营/订单管理员 | 订单修正、客户归并、业务配置、数据质量管理 |
| 合作医院操作员（后续） | 仅其医院的预约、到院、服务确认和核销事项，不可访问无关客户或其他医院数据 |

界面入口：PC 管理后台；企业微信内部应用工作台（移动端）；适配手机的客户建档、日沟通、核销/预约表单。

## 4. 客户信息表 → 客户档案中心（P0）

### 4.1 关键字段

`customer_id`（系统生成）、客户姓名/称呼、企业微信昵称、手机号（可空）、手机号验证状态、客户来源、所属管家、所属团队、企业微信关联身份、客户标签、会员状态、创建时间、最近沟通时间、备注。

同一客户可关联多个企业微信联系人关系或多个管家历史；需要客户转移记录与历史归属。客户姓名及手机号采用系统选取和自动回填，不允许在其他表格随意覆盖客户主数据。

### 4.2 重要改动：不再把微信昵称填进手机号列

原 Word 的日终规则允许“没有手机号时把微信昵称暂写入客户信息表的手机号列”，这是为适应表格以手机号做关联键的临时办法。CRM 中应改为：手机号为空，保留微信昵称及 `customer_id`；通过企业微信外部联系人映射或系统选择器关联记录，后续再更新手机号。电话号码去重仅作为辅助提示，不能作为唯一判断依据。

### 4.3 客户建档流程

企业微信新增外部联系人 → 事件/周期同步 → 通过 `external_userid` + 企业上下文匹配 → 有则关联，无则建立待完善客户档案 → 分配管家 → 后续补齐实名与手机号。手工建档遵循相同去重逻辑；客户合并由管理员审核，保留所有历史订单归属与操作日志。

### 4.4 字段计算、同步及迁移约束（V1.2 增补）

1. **客户创建与录入**：用户姓名、客户昵称、电话、所在城市、备注、备注名可由授权人员填写或合法来源同步；“填写者（填写账号名称）”“提交时间”优先由系统记录，不能由客户端任意伪造。
2. **归属关系**：“所属管家（真实姓名）”与“所属账号”是不同字段。前者关联员工真实身份；后者具体含义可能为账号归属，但截图不能证实，必须业务确认后定义外键和迁移方法。
3. **公式与关联**：“关注项目”“电话-是否重复”“订单总金额”“卡点情况”在截图中显示公式图标；“客户来源”“客户渠道”“下单数”显示关联/查找类图标。开发前导出实际公式、关联表、选项值及样例数据，不要根据本说明自行臆造原有计算公式。
4. **订单汇总口径**：保留“下单数”“订单总金额”的原字段及迁移结果；额外提供“有效订单数、累计实付、成功退款、在用权益余额”等独立指标。**订单总金额≠累计实付金额**，旧公式与新口径要在样本对账后确定。
5. **多时间字段**：提交时间、客户首次入库时间、客户添加时间、首次下单时间、最后一次跟进时间均独立迁移。没有来源解释时不得把它们统一映射为 `created_at`。系统可额外存服务器创建/更新时间。
6. **客户状态/新老客**：保留当前值和原选项，等取得原表配置后再确定状态机和自动识别口径；升级时不能仅因 CRM 设定新状态而改变历史数据。
7. **卡点分析**：保留原“卡点情况”字段和其公式结果；AI 可生成 `ai_bottleneck_suggestion` 等独立字段，待管家确认后再转入正式跟进记录。
8. **客户去重**：手机号校验只给出“疑似重复”及其证据；同号多人、无号客户、不同企业微信身份均不得自动合并。每笔合并需审批、保留源记录与关联审计。
9. **字段必填与权限**：截图仅展示字段名称及图标，并未展示是否必填、公式内容、是否对管家可编辑、字段选项。实际必填清单和编辑权限需用原表设置+真实样本核实。

## 5. 日沟通情况表 → 沟通时间线（P0）

### 5.1 忠实继承原填报规范

原 Word 必填项：客户电话（从客户选择列表选，而不是手输）、沟通内容；选客户后自动带出姓名。沟通内容建议包含日期、方式、沟通要点、客户意向、下一步计划；同一客户每次沟通新增一条，不得覆盖旧内容；成交日期非必填，只有明确成交后才能记录。

在 CRM 中将“选择客户”替换为客户选择器（支持昵称、姓名、手机号、企业微信身份检索），手机号不再强制必填。

### 5.2 自动化录入与人工录入

- 企业微信归档的每条消息：保留消息 ID、发送方向、发送人、时间、类型、原始内容/媒体引用及客户关联；只处理合法授权范围的消息。
- 按会话窗口生成“沟通摘要”：AI 输出本次谈了什么、意向项目、医院、价格、预约/投诉/退款线索、下一步建议和证据消息 ID；摘要为待核实，管家可编辑确认。
- 电话、面谈、其他合法线下沟通：管家手机端选择客户，填写方式、时间、要点、下一步安排；同一沟通不重复生成多份待办。
- 未确认身份的聊天：进入“客户关联待核对”，不得自动并入仅姓名相似的客户。

### 5.3 成交识别规则

区分 `AI疑似成交`、`管家确认成交`、`订单已生成`、`支付已确认` 四种状态。聊天中出现“我要买”“帮我下单”只自动生成待确认线索；仅当员工依据确认规则操作或支付回执完成核验，才进入正式订单流程。为了兼容旧习惯，日沟通表仍可显示“成交日期”，但它不再单独决定支付成功。

## 6. 售卖登记表 → 订单及支付管理（P0）

### 6.1 订单字段

| 分类 | 字段 | 校验 |
|---|---|---|
| 身份 | 订单编号、客户ID、客户姓名、所属管家、创建人、来源沟通ID、订单日期 | 编号全局唯一；客户姓名自动读取 |
| 项目 | 套餐/卡项名称、订单行项目、项目数量/次数、项目单价或分摊金额 | 必须至少有一项；支持套餐多个子项目 |
| 金额 | 订单原价、优惠金额、实付金额、已退款金额 | 金额使用 decimal，禁止前端字符串计算 |
| 支付 | 线上/线下支付方式、支付时间、支付流水号、付款凭证、支付确认人 | 线下付款附件/截图支持上传；按交易流程核验 |
| 服务 | 关联医院（若已确定）、权益有效期、已核销次数/金额、剩余次数/金额 | 汇总从权益和核销流水计算，禁止手改 |
| 流转 | 草稿、待核验、已支付、部分履约、已完成、退款中、部分退款、已退款、已取消 | 每次状态变化写入审计日志 |

“订单金额”保留为优惠前金额，“订单实付金额”为优惠后实际支付金额。必须区分账面订单金额、已支付金额、退款金额及未消费权益金额，不可用其中一个数值代替其他数值。

### 6.2 订单创建链路

1. 管家确认成交/支付线索，系统读取客户、管家、沟通和成交时间。
2. 生成唯一**订单草稿**；前端补齐项目、次数、原价、实付及付款凭证。线上直接同步到原交易系统订单号；未沟通直接自主下单走“订单导入/自主下单”入口。
3. 支付由财务/受信支付来源确认后，订单转为“已支付”，发放项目权益并记录来源流水。
4. 同一个沟通触发事件不得生成重复草稿；未支付/取消的订单不得计入累计实付与可用权益。

### 6.3 线下凭证规则（待确认）

原 Word 要求“线下订单付款截图”，并希望包含付款日期、到院机构和付款金额，但在原文里备注了“是否算与机构沟通的？待确认”。CRM 应将支付凭证、机构结算凭证、客户沟通截图分成不同附件类别。上线前由业务确认哪些是强制附件、何种情形必须显示医院。

## 7. 会员套餐、项目权益与金额核算（P0）

### 7.1 核心对象

`服务项目目录`、`套餐模板`、`套餐包含的项目`、`客户订单行`、`客户可用权益`、`权益增减流水`。

支持一次购买多个项目、不同项目次数、赠送项目、有效期、适用医院或服务限制、延期和经审核的权益调整。**不允许仅记录“一个套餐剩余 8 次”而无法知道是哪种项目。**

### 7.2 权益流水与余额

- 发放：订单支付确认后按每个项目产生正向权益流水。
- 使用：医院服务完成并经有效确认后产生核销与负向权益流水。
- 退款：按退款申请实际对应的未消费权益回收次数或金额；部分退款必须有分摊规则。
- 错误处理：撤销/冲正追加相反方向流水，保留原记录、原因、审批人和时间。
- 失效：到期转不可用，保留历史购买与核销情况，不计作已消费。

**单项目可用次数 = 已发放次数 + 有效增补/冲正 - 有效核销次数 - 已回收次数 - 其他已确认调整。**

**金额计算注意**：原 Word 同时要求“已核销总额、剩余未核销金额”。实际分摊金额应按订单行、优惠、退款及业务定价规则计算；不能直接用“订单实付总金额÷套餐全部次数”，除非业务已确认所有项目等价。建议单独存订单项的分摊实付金额，流水汇总出金额报表。

## 8. 订单核销明细表 → 医院到院与核销（P0）

### 8.1 必填信息

客户、订单号、订单行/具体项目、合作医院、预约时间（如有）、实际到院时间、服务日期、核销次数、核销金额、医院确认状态、提交人、核销时间、附件/备注。系统带出客户和订单已有字段，管家只录本次变化的数据。

### 8.2 操作流程

选择客户/订单 → 点击“新增核销” → 选择具体项目与医院 → 填本次核销次数、日期及金额 → 校验权益是否充足、是否重复 → 医院或有权限人员确认 → 执行一次事务提交核销记录 + 权益流水 + 订单汇总视图。

旧智能表通过复选框勾选—取消—再勾选来创建新核销行；新 CRM **不建议照搬为布尔值触发器**。可保留列表中的快捷核销按钮，避免重复点击、网络重试或复选框重置产生重复核销。每次服务一条独立记录。

### 8.3 更正机制

原 Word 一方面要求“不要修改历史核销记录”，另一方面在常见问题中允许更正错误金额并注明修改时间、事项。新系统采用：普通管家不可直接覆盖有效核销记录；由有权限人员发起更正，追加冲正和新核销流水，原记录仍可查看。跨月更正需注明原因并走更高级审核（具体审批角色待确认）。

### 8.4 医院对账

按医院、日期、项目、管家汇总预约、到院、有效核销次数和确认金额；支持医院凭证上传、Excel 导入和后续医院接口对接。来自聊天的“我上周去做过一次”只能生成待核对的到院线索，不自动扣减次数。

## 9. 退款管理（P0，新需求）

客户详情必须可见退款申请、退款审批、退款执行、实际到账/原路退回、关联订单、具体退款项目、退款金额和权益回收明细。状态建议：`待受理 → 审批中 → 待执行 → 退款成功/失败/驳回/撤销`，部分退款可多笔。

AI 可识别“我要退款”“不想继续做了”等诉求并标记风险，**绝对不能据此将订单认定为已退款**。只有财务的实际付款退回记录或受信支付通道的成功回执才能确认成功退款。已消费项目退款、未消费项目退款的金额分摊规则须另行确定。

## 10. 回访、预约与每日检查（P0）

### 10.1 回访任务

自动/手动创建 `followup_tasks`，包含客户、管家、类型、触发原因、关联证据、计划时间、到期时间、状态、处理结果。示例触发：成交后未预约、完成服务后的既定回访周期、剩余权益长期未消费、即将到期、客户询问档期、退款/投诉待处理。规则可按项目配置，避免医疗服务时间表由通用 AI 自行决定。

### 10.2 将原文“每日必做清单”变成系统规则

| 原日终检查项 | CRM 自动判定/提醒 |
|---|---|
| 今日沟通是否登记 | 企业微信可存档会话已同步且有关联摘要/待处理状态；手工沟通缺记录提示补录 |
| 客户身份字段是否完整 | 客户关联待核验、姓名/手机号缺失分开提示，不能以假手机号过关 |
| 今日成交是否记录成交日期 | 识别到待确认成交意向但未处理；已确认成交无订单草稿提示 |
| 自动生成的销售记录是否补齐 | 待完善订单缺项目、金额、次数或支付凭证，列入待办 |
| 今日到店是否生成核销 | 到院已确认但未核销、核销草稿未提交，触发核验提醒 |
| 剩余未核销金额是否正确 | 定期重算订单项及权益流水，与汇总/对账记录比对，差异进入异常队列 |

增加日报：今日新客户、沟通次数、确认成交笔数、核销笔数、回访完成率、待处理退款、数据异常清单。按管家、团队、医院和日期过滤。

## 11. 企业微信官方接入（P0）

### 11.1 接入边界

- **允许**：企业微信客户联系 API 同步外部联系人、跟进员工与企业标签；已开通且在许可范围内的会话内容存档通过官方 SDK 增量采集，解密并归档。
- **不允许**：个人微信消息抓取、Hook、模拟登录、非官方协议、代替员工随意发送普通微信私聊。
- **前提条件**：企业微信会话存档的开通条件、成员范围、客户同意、密钥管理、存储与保留政策须由实际企业环境确认。

### 11.2 采集链路

企业微信客户事件/消息通知 → API 同步或存档增量拉取 → 官方 SDK 解密 → msgid 去重/断点恢复 → 客户身份关联 → 原始消息安全存储 → AI 异步分析 → 客户时间线/待办建议。

关键字段：企业标识、应用标识、`external_userid`、内部成员 ID、会话消息 ID、`seq`、消息类型、发送时间、消息归档和解密状态、客户关联状态、原文证据引用、采集错误信息。

### 11.3 可靠性要求

记录存档拉取游标；按消息 ID 唯一去重；定时增量拉取并补偿重试；监控最后成功同步时间、积压消息、解密错误、无法关联客户数、API 限流与权限异常；禁止把不确定的历史数据当作已经完整同步。由于接口的历史可获取窗口有限，需要持续抓取和自有归档，不依赖临时拉取长期历史。

## 12. AI 智能管家功能（P1；P0 预留字段和事件）

### 12.1 AI 处理对象与输出

AI 使用合规归档的对话、客户实际订单和权益数据进行分析。输出包括：本次聊天摘要、客户项目意向、询价/预约/到院/退款/投诉信号、建议回访日期、拟建任务、证据消息 ID、置信度、人工确认状态、处理备注。

### 12.2 典型意图与处理

| 识别内容 | 自动创建什么 | 不允许自动做什么 |
|---|---|---|
| “下周想去做一次” | 预约待办、候选项目 | 不确认医院档期、不核销 |
| “我上周已经做过” | 到院/核销核对任务 | 不直接扣次数 |
| “剩下还有几次” | 以数据库权益余额生成建议回复 | 不凭聊天自行改余额 |
| “我要退款” | 退款诉求、优先处理提醒 | 不自动确认退款成功 |
| “我要买/付款了” | 成交意向、待核验订单草稿 | 不未经支付/员工确认计实付 |
| “效果不好/想投诉” | 服务异常工单、负责人提醒 | 不擅自给出医疗诊断和效果保证 |

### 12.3 AI 输入与防护

AI 作为辅助处理层，必须隔离敏感数据、执行角色权限、保留原文引用和业务可解释性；聊天中的任意内容不得被当作系统指令来改变权限、调用退款接口或导出客户资料。AI 无直接修改已支付订单、核销流水、退款成功标识的权限。对于消息包含的健康与医疗信息，需要授权、最小必要处理与供应商数据边界评估。

## 13. 客户详情页与经营看板（P0/P1）

客户详情页单屏摘要包括：姓名/昵称、企业微信关联、专属管家、累计订单原价、累计实付、成功退款、当前有效权益数、各项目剩余次数/金额、最近医院、最近已确认核销、下次预约、最近沟通摘要、待处理投诉/退款、AI 建议跟进事项。

子页签：基本资料｜沟通时间线｜订单与支付｜会员权益｜预约与医院｜核销｜退款｜AI 事件｜回访历史｜审计记录。

老板看板：新增客户、成交/实付、成功退款、已确认核销次数/金额、剩余可用权益、各医院履约、管家任务完成率、沉睡客户、到期预警、数据质量异常。所有指标都明确口径（实付按入账日、退款按成功日、核销按有效确认日），不能混用。

### 14.1 核心事务约束

核销采用数据库事务，锁定目标权益、验证剩余次数、创建唯一核销单、追加权益变动流水并更新必要的聚合快照。退款同理按订单项回收权益；所有成功事件具备唯一 `source_event_id` 防重入。对账任务从不可变流水重算结果，识别负数权益与重复事件。

## 16. 核心状态机

**客户沟通成交**：`沟通记录 → AI疑似成交（可选） → 管家确认 → 订单草稿 → 订单信息完善 → 支付确认 → 权益发放`。

**预约与核销**：`待预约 → 已预约 → 到院待确认 → 已到院 → 服务已确认 → 核销成功`；取消预约与未履约不扣次数；错误核销走“冲正→重新核销”，不删除事实流水。

**退款**：`申请 → 待审批 → 待执行 → 成功/失败/驳回/撤销`；只有成功状态产生财务退款事实，涉及未消费权益时创建对应回收流水。

**AI 任务**：`待识别 → 已识别待核实 → 已确认/驳回 → 已分配 → 处理中 → 已完成/关闭`；同一原始消息重复分析不会创建重复任务。

## 17. 验收测试用例（第一版必须覆盖）

1. 无手机号但有企业微信昵称的客户成功建档，沟通和订单关联正常。
2. 同一个客户一天沟通 3 次，有 3 条独立记录且按时间显示。
3. 管家新增沟通后，客户姓名自动带出，无须手输，修改客户信息不会更改历史原始聊天内容。
4. 日沟通中提到“我要买”，仅生成成交线索，不自动增加实付。
5. 一个已确认成交线索重复点击三次，仍只生成一张订单草稿。
6. 未沟通直接线上成交，可通过自主下单/导入入口建订单。
7. 未填写项目次数或实付等关键字段的订单无法进入完成校验的已支付状态。
8. 一个套餐包含项目 A 10 次、B 6 次，核销 A 不影响 B 次数。
9. 同一次核销因网络重试提交两次，只扣一次权益。
10. 剩余 0 次时无法再次成功核销，且没有负数权益。
11. 到院登记而未服务确认，不扣次数。
12. 客户说“已去医院”，AI 生成待核验线索，不自动核销。
13. 同一客户在两家医院核销，分别保留医院和时间。
14. 核销错误按权限冲正，原记录可追溯，余额回算正确。
15. 线下订单付款凭证可上传、查看并受权限控制。
16. 部分退款批准但财务未打款，不能增加“成功退款”。
17. 已成功退款按订单项回收对应权益，核销历史不被删除。
18. 企业微信归档授权范围外的消息不采集；采集服务延迟/失败会报警。
19. 企业微信消息重复抓取不会重复生成原文和 AI 待办。
20. 管家只看到自己负责的客户；主管、财务、医院人员遵循角色范围。
21. 日终列表发现缺核销、缺订单必填字段和未处理成交线索。
22. 报表订单实付、核销金额、退款金额与流水对账一致。

## 18. 分阶段实施和 AI 开发交付

### 阶段 1（P0）：CRM 业务闭环

客户档案、组织权限、项目/套餐、沟通人工登记、订单/支付、权益流水、预约、医院核销、退款、日终检查、Excel 导入、审计日志。此阶段不依赖企业微信和 AI，也必须保证资金与权益准确。

### 阶段 2（P0）：企业微信接入

客户联系、身份关联、会话存档合规配置、增量拉取、媒体处理、消息检索与监控。先做消息归档可靠性验证，再给 AI 消费数据。

### 阶段 3（P1）：AI 智能管家

聊天摘要、意图识别、预约/退款/投诉线索、证据定位、人工核实、智能待办、客户摘要、回复建议；严格禁止自动改正式余额与退款事实。

### 阶段 4（P1）：运营看板与多院协作

管家工作量、医院对账、退款效率、到期与沉睡客户、复购与流失分层；合作医院可选安全协作门户或接口。

### 每阶段交付标准

开发文档、数据库迁移脚本、OpenAPI 接口、权限矩阵、UI 页面、测试用例、部署脚本、示例数据、日常备份恢复方案、问题与操作手册。推荐技术：Vue 3 + TypeScript + Element Plus；FastAPI；PostgreSQL；Redis + Celery；MinIO；企业微信官方 SDK；Nginx + systemd。优先模块化单体，避免第一版过度拆微服务。

| 核销金额更正 | 一处禁止修改历史，一处允许修改并备注（跨月尤其如此） | 采用追加式冲正与重新核销，审批分级；运营/财务确认 |
| 客户无手机号 | 原文临时把微信昵称填在手机号列 | 保留昵称但手机号空，改用 customer_id + 企业微信身份关联 |
| 已核销总额与剩余金额 | 原文要求自动累计、公式计算 | 按订单行和实付分摊规则算账；确认跨套餐、赠送、优惠、退款场景 |
| “每 9 打勾一次” | 文中疑似排版或录入错误 | 依据上下文按“每次勾选产生一次核销记录”理解，不按“9 次”实现；业务确认 |

## 20. MVP 完成定义

**第一版合格，不是“有这些页面”，而是能走通一位客户的完整生命周期：**新建客户 → 连续沟通记录 → 成交确认并填写订单 → 支付核验 → 发放每个项目的权益 → 预约与到院 → 真实服务核销 → 项目次数/剩余金额自动计算 → 发起与完成退款 → 日终漏单提醒 → 按客户和医院查历史。所有关键环节均有操作者、时间与证据。

AI 和企业微信分阶段接入后，新增的是“自动获得沟通线索、自动生成任务、辅助回复”，不替换上述不可缺少的业务事实链。

## 21. V1.3 新增范围概述（新增来源：九类现用业务表截图及全流程图）

## 23. 正式业务状态机与资金口径

订单不等于支付、支付不等于平台实收、到院不等于核销、核销不等于机构已结算、退款申请不等于成功退款、同客户不同医院消费必须逐笔留存。客户付平台/客户付医院/医院与平台清分分别建账。具体见 `02`、`03`、`06` 文档。

## 24. 达人、公域和社群获客

允许登记达人个人账号在公域发布的合作内容及推广效果；**绝不触碰个人微信私聊采集**。通过企业微信官方“联系我”渠道参数、销售归属、活动编号等可证明的数据将客户来源回链达人与商务。多人归因按审核过的规则版本执行；客户隐私仅授权人员可见。
